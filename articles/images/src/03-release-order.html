Actions → Release → Run workflow

Release, in the order that makes failure cheap

The only input is the bump: patch, minor or major. Everything below is derived from it, and the changelog is generated before the commit that carries it exists — so the notes never list their own release.

1
dispatch
Choose patch / minor / major. There is no free-text version field.
2
pnpm version <bump>
Rewrites package.json only — the root version is not in pnpm-lock.yaml, so no lockfile churn.
3
git-cliff --tag vX.Y.Z
Regenerates the whole changelog before the release commit exists, so the notes never list themselves.
nothing irreversible above this line
4
commit · tag · push
chore: release vX.Y.Z and the tag, pushed to main together.
5
pnpm build && verify
The tarball is built and checked with publint + attw again, from the tag that was just pushed.
6
pnpm publish --provenance
Trusted publishing over OIDC: no token in the repository after the first release.
7
GitHub release
Last, from the generated notes — so a failed publish never leaves a release pointing at a version that is not on npm.
If the publish fails: delete the tag, revert chore: release vX.Y.Z on main, dispatch the same bump again. Ticking dry_run generates the changelog, builds and verifies the package, then prints the notes and the exact file list npm pack would upload.
